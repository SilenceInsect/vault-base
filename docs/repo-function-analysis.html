1. 仓库定位

vault-base 是团队「共享知识金库底座」：为任意业务 Skill 提供统一的知识检索、本地沉淀与（可选）共享同步链路。自身不承载某个业务领域的专属知识，而是提供可接入的基础设施。

层存储职责
本地 Vaultreferences/vault/**/*.md（Obsidian）单机笔记、brief、候选共享前落盘
共享金库MySQL amrd_qa_vault + Redis 缓存/事件跨 Skill 可复用结论；审核后进 main
真相源布局~/common-skills-repo/vault-baseCursor/Claude/Codex 通过 junction 联接，避免多份拷贝
边界：本仓只管 vault: / amrd_qa_vault；领域库（如 bug-vault / amrd_qa_kb）仍由领域 Skill 维护。协议要求「叠读、不替换源」，P0/P1 禁止把业务默认读源切到公共库。

3. 功能实现逻辑

3.1 就绪门禁（R1–R8）

readiness_gate.py 产出契约：ready / gate / capability。can_write_shared=false 时禁止一切共享侧写入。

项含义缺失等级
R1本地 Vault 有 mdDEGRADED
R2Redis PING + MySQL SELECT 1DEGRADED
R3Vault 有 Git HEADBLOCKER
R4DB 身份回读正确（防静默 SQLite 却写 Redis）BLOCKER
R5–R8业务 Skill accepts_brief / brief / samples / 迭代字段按项 DEGRADED/INFO

3.2 检索（协议强制顺序）

0 skill_catalog→ A 共享 Redis→MySQL→ B 本地 Vault MD→ C 领域金库→ D 资料原文→ E 问用户

索引只做路由与元数据合并，不替代正文召回。协议已声明：统一 recall CLI/API 尚未实现；目前 lookup 只产出 lookup_plan。

3.3 沉淀（写路径）

  1. vault_dump 生成带 frontmatter 的 MD（answer/decision/reference） 落 answers|decisions|references/{uuid}.md；content_hash 幂等；redact 命中 → is_candidate_shared=false
  2. 候选共享 仅当 frontmatter 标记且门禁允许 禁止业务直写 shared_vault_main；必须走事件 → pending → 审核
  3. 审核通过 approve → main（status=active） 拒绝 / supersede 保留审计；检索默认只返回 active

3.4 事件队列（Redis 3.2 LIST）

因 Redis 3.2.12 无 Stream，采用 LIST + BRPOPLPUSH；按 user_id 分片。

生产 LPUSH  vault:events:{user}
取出 BRPOPLPUSH → vault:processing:{user}
确认 LREM processing
失败 LPUSH vault:dlq:{user}
暂存 LPUSH vault:llm_pending:{user}   # timer 模式规则判不了

基线推进时机：入队成功后（避免消费失败导致重复扫描却永不前进）。消费侧按 event_id 幂等。

3.5 存储抽象错位（关键）

DDL（真相） 使用表 shared_vault_pending_review / shared_vault_main / vault_event，字段含 segments、tags、skill_id 等。
MysqlVaultStore（代码） 仍按 Sqlite 简化模型读写 meta_json、vault_events 等不存在的列/表 → 审核、搜索、事件落库在 MySQL 路径下必然失败。

4. 工作流时序

4.1 安装时序（一次性）

clone → common 仓→ link IDE→ install_inventory→ secrets.local.json→ env_ensure→ readiness_gate→ DDL（已建空表）

4.2 会话内业务时序（每次任务）

  1. 第 0 步门禁env_ensure → readiness_gate；有 BLOCKER 则中止；注入 briefs/{skill_id}.md
  2. 技能索引skill_catalog scan/lookup → 合并元数据 → lookup_plan
  3. 叠读召回共享 → 本地 Vault → 领域库 → 原文 → 提问（召回门面待实现）
  4. 执行业务业务 Skill 自身逻辑（如一致性审查）
  5. 结案沉淀vault_dump（可复用结论）+ 领域原写入（领域资产）
  6. 增量入队（联网）git commit Vault → scan → queue enqueue → consume → pending
  7. 人工审核vault_review approve/reject → shared_vault_main

下列结果来自 2026-09-28 对本机 C:\Users\\common-skills-repo\vault-base 的命令探测，非文档推演。

5.3 闭环可读结论

本地半闭环可用：安装联接 → 门禁 → 索引 → dump → 读本地 brief/笔记。
共享全闭环不可用：即使 Redis/MySQL 连通且 can_write_shared=true，消费端无法启动，审核/检索 SQL 与 DDL 不匹配，共享表仍为空。知识无法从「本机 MD」走到「团队可检索 active」。

6. 阻断根因（按严重度）

级别问题影响
P0 MysqlVaultStore SQL 与 ddl_mysql57.sql 字段/表名不一致（meta_json、vault_events vs segments/vault_event） pending upsert、list、approve、search 全挂
P0 vault_consume.py 错误导入 load_secrets/redis_conn 事件消费 Agent 无法启动
P1 缺少统一 recall 门面；业务只能靠 Agent 读协议手工叠读 共享召回不可自动化、不可测
P1 install_inventory Windows 路径 YAML 转义 其他团队安装引导在本机路径场景失败
P2 scan 硬编码 user/skill；文档写 --user 但 CLI 无此参数 多用户/多 Skill 事件归属错误风险
P2 共享表空 + 本地几乎无 answer/decision 语料 即使修好代码，短期内检索也无内容可命中

7. 建议优先级

  1. 对齐 MysqlVaultStore ↔ DDL 按 assets/ddl_mysql57.sql 重写 insert/select/approve/search；事件表用 vault_event；审计字段对齐 snapshot/reason
  2. 修复 vault_consume 导入 从 vault_secrets 导入；补一条 session --once 冒烟（dump→commit→scan→enqueue→consume→review list）
  3. 补 recall CLI 统一 A+B，返回带 source 标签的命中；lookup_plan 仅作路由输入
  4. 修 install_inventory 路径序列化 Windows 路径用正斜杠或 YAML 单引号/字面块
  5. 打通一条真实共享样本 选一条非敏感 decision，走完 pending→approve，验证 FULLTEXT 检索
一句话结论：vault-base 作为「本地知识底座 + 环境门禁 + 技能索引」已经可用；作为「团队共享金库闭环」因 MySQL 适配层与消费入口缺陷尚未生效。门禁绿灯不能等同于共享链路可用。
