1. 仓库定位

vault-base 是团队「共享知识金库底座」：为任意业务 Skill 提供统一的知识检索、本地沉淀与（可选）共享同步链路。自身不承载某个业务领域的专属知识，而是提供可接入的基础设施。

层存储职责
本地 Vaultreferences/vault/**/*.md（Obsidian）单机笔记、brief、候选共享前落盘
共享金库MySQL amrd_qa_vault + Redis跨 Skill 可复用结论；审核后进 main；vault:c: prefixCache
决策门控本机 laya-serve（可选）共享候选结构化判定；不替代人审
真相源布局~/common-skills-repo/vault-baseCursor / Claude / Codex / Workbuddy 等 junction 联接
边界：本仓只管 vault: / amrd_qa_vault；领域库（如 bug-vault / amrd_qa_kb）仍由领域 Skill 维护。协议要求「叠读、不替换源」。

3. 功能实现逻辑

3.1 就绪门禁（R1–R8）与安装门禁（I1–I9）

readiness_gate 管连通与本地骨架；共享开启后必须再跑 install_gate --require-shared（I1–I9），否则不能宣称共享可写。

项含义
R1–R8Vault / Redis·MySQL / Git / DB 方言 / 业务 brief 等
I1–I2IDE LINK；物料清单 YAML（Windows 路径规范化）
I3–I6DDL↔MysqlVaultStore；consume 可导入；pending / search
I7–I9Redis LIST；空队列 BRPOP；prefixCache vault:c:

3.2 检索顺序

0 skill_catalog→ A Redis vault:c:→ A′ MySQL main→ B 本地 Vault MD→ C 领域金库→ D 资料原文→ E 问用户

统一门面：vault_recall.py / vault_cache_ask.py。prefixCache 与事件队列键分离（见 references/prefix-cache.md）。

3.3 沉淀（写路径）

  1. vault_dump 落 answers|decisions|references/{uuid}.md；content_hash 幂等；redact → is_candidate_shared=false
  2. 候选共享 禁止业务直写 main；事件 → 规则/Laya 判定 → pending → 人审
  3. 审核通过 approve → shared_vault_main（active）并写穿 prefixCache

3.4 事件队列（Redis 3.2 LIST）

无 Stream，采用 LIST + BRPOPLPUSH；按 user_id 分片。

生产 LPUSH  vault:events:{user}
取出 BRPOPLPUSH → vault:processing:{user}
确认 LREM processing
失败 LPUSH vault:dlq:{user}
暂存 LPUSH vault:llm_pending:{user}   # timer 模式规则判不了

基线推进：入队成功后。消费按 event_id 幂等；空队列超时视为无事件（不抛死）。

3.5 消费判定（规则 → Laya）

非候选 / redact→ private
候选共享→ 规则→ Laya share_gate→ private | share | uncertain→ pending（永不自动 approve）

默认 laya.enabled=false。开启后打本机 POST {base_url}/v1/systemone。旧配置键 jev.* / jev_client.py 仍兼容回落。

3.6 存储（已对齐）

DDL 真相：shared_vault_pending_review / shared_vault_main / vault_event 等，字段含 segments、tags、llm_verdict…
MysqlVaultStore：已按 DDL 读写（历史 meta_json / vault_events 错位已修复，由 I3/I5/I6 门禁兜住）。

4. 工作流时序

4.1 安装时序

clone → common 仓→ link IDE→ install_inventory→ secrets.local.json→ env_ensure→ readiness_gate→ DDL→ install_gate --require-shared

步骤细节见 docs/install.html。

4.2 会话内业务时序

  1. 第 0 步门禁env_ensure → readiness_gate；注入 briefs/{skill_id}.md
  2. 技能索引skill_catalog scan/lookup → lookup_plan
  3. 叠读召回vault_recall / cache_ask：共享缓存 → MySQL → 本地 → 领域
  4. 执行业务业务 Skill 自身逻辑
  5. 结案沉淀vault_dump + 领域原写入
  6. 增量入队git commit → scan --enqueue → consume（规则/Laya）→ pending
  7. 人工审核vault_review approve/reject → main + prefixCache

4.3 事件消费双模式

模式场景能力
sessionP1/P3/P4 会话内可开 Laya；uncertain 仍入 pending
timerP2 定时任务规则 +（可选）Laya；判不了 → llm_pending

4.4 共享候选闭环

6. Laya 本地部署与微调

托管 JEV（openclaw-api.com /v1/decisions）已改为开源 Laya 本地方案。契约：references/laya.md。

6.1 部署

pip install "laya[serve]"
set LAYA_HOST=127.0.0.1
set LAYA_PORT=8000
set LAYA_DEVICE=cpu
set LAYA_PRELOAD=1
set LAYA_MODELS=typed-decisions
laya-serve

# vault.config.json
"laya": {
  "enabled": true,
  "base_url": "http://127.0.0.1:8000",
  "api_path": "/v1/systemone",
  "model": "typed-decisions"
}

python scripts/laya_client.py probe
python scripts/laya_client.py share-gate --candidate-shared --title "..." --question "..." --answer "..."

6.2 从 Vault 已有决策做训练集

python scripts/laya_export_dataset.py
# 输出：references/vault/_kb/laya_finetune/share_gate.jsonl

2026-09-29 导出实况：合计约 5 条（3 种子 + 1 本地 private smoke + 1 MySQL share smoke）。仅够链路冒烟；正式 RLCD 微调建议 ≥200 条人审标签，再接上游 notebook（见 Laya Fine-tune 指南）。

6.3 与 CC Switch / OpenAI Chat 的关系

CC Switch 的 OpenAI 兼容网关不能直接填进 laya.base_url（缺 /v1/systemone）。要用 Chat 网关需另做 backend=chat 适配；当前推荐路径是本机 laya-serve。

8. 建议优先级

  1. 持续沉淀真实决策 / 答案 vault_dump → commit → scan → consume → 人审；扩充 main 与微调 JSONL
  2. 本机启用 Laya（可选） laya-serve + laya.enabled=true；用导出集跑上游 RLCD notebook 后换 checkpoint
  3. legacy_vaults 纳入 按物料清单 review_then_import，扩大可检索语料
  4. 业务 Skill 薄封装 领域 query 与 vault_recall 并行 merge（协作协议待办）
一句话结论：vault-base 作为本地底座 + 共享闭环基础设施已可用；当前短板是知识语料与 Laya 训练样本，不是消费/审核链路本身。安装请以 install_gate 为准，勿只看 readiness 绿灯。
